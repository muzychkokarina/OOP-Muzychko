## Висновки
Для методу `ParseInt` використання винятку `InvalidInputException` є доцільним, оскільки метод повертає примітивний тип `int` і за контрактом зобов'язаний надати валідне число або перервати обчислення при порушенні передумов (нечисловий рядок). Натомість для `ValidateString` перевірка довжини рядка є типовою бізнес-валідацією, де невдача є нормальним і очікуваним результатом перевірки — патерн `Result<bool>` робить потік виконання прозорим і позбавляє витрат на розгортання стека винятків.

## Відповіді на контрольні запитання

1. **Навіщо створювати власні типи винятків? Які переваги це дає?**  
   Власні винятки дозволяють точно виражати специфічні помилки бізнес-логіки або доменної області, відокремлюючи їх від системних збоїв. Це дає змогу перехоплювати конкретні помилки у блоках `catch (CustomException)` та передавати структуровану діагностичну інформацію через додаткові властивості класу винятку.

2. **Які стандартні конструктори рекомендується реалізовувати для власних винятків?**  
   Згідно з рекомендаціями .NET, клас винятку має містити:
   - конструктор без параметрів `MyException()`;
   - конструктор з повідомленням `MyException(string message)`;
   - конструктор із повідомленням та внутрішнім винятком `MyException(string message, Exception innerException)` (для збереження ланцюжка першопричин);
   - захищений конструктор серіалізації `MyException(SerializationInfo info, StreamingContext context)`.

3. **Поясніть патерн Result. У яких випадках його використання є більш доцільним, ніж викидання винятків?**  
   Патерн `Result<T>` інкапсулює підсумок операції в одному об'єкті, який містить ознаку успіху (`IsSuccess`), значення (`Value`) або опис помилки (`Error`). Його доцільно використовувати при валідації користувацького вводу, пошуку сутностей, які можуть бути відсутніми, або порушенні бізнес-правил, де помилка є очікуваним сценарієм, а не аварійним збоєм.

4. **Які сценарії краще обробляти через винятки, а які через патерн Result?**  
   - **Через винятки:** непередбачувані технічні або інфраструктурні збої (відсутність з'єднання з БД, помилки вводу/виводу, нестача пам'яті, порушення інваріантів конструктора або критичних контрактів методів).  
   - **Через патерн Result:** очікувані сценарії невдачі в штатному потоці програми (некоректна довжина пароля, невірний формат email, недостатньо товару на складі, невдала перевірка бізнес-умов).
